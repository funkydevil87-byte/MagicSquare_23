# STEP 1 — Observation (관찰)

워크스페이스(`MagicSquare_23`)에는 아직 코드나 문서가 없습니다. 따라서 아래는 **지금 주어진 상황(의도 + 빈 프로젝트)**을 관찰한 결과입니다.

---

## 1. 현재 우리가 해결하려는 상황은 무엇인가?

**한 사람이 4×4 격자에 1부터 16까지의 정수를 한 번씩 배치했을 때, 행·열·대각선 합이 모두 같은 “균형 조건”을 만족하는 배치를 찾거나 검증·생성하려는 상황**입니다.

관찰 관점으로 풀면:

- **입력/출력**: 16칸 격자와 16개의 서로 다른 숫자(1~16)가 주어지거나, 프로그램이 그런 배치를 제시함
- **제약**: 각 숫자는 정확히 한 칸에만 존재; 여러 “선(line)”(4행, 4열, 2대각선)의 합이 동일해야 함
- **불확실성**: “모든 배치”를 나열할지, “하나만” 만들지, “유효한지 검사”만 할지는 아직 명시되지 않음
- **맥락**: 폴더명과 대화로 보아, **아직 구현 전인 학습·연습용 과제**로 문제를 먼저 정의하려는 단계

즉, “프로그램을 만든다”기보다 **“16개 숫자의 배치가 여러 선의 합 균형을 만족하는지, 어떻게 그런 배치에 도달하는지”를 다루는 상황**입니다.

---

## 2. 왜 4×4 마방진 문제를 다루는가?

관찰 가능한 **동기(가설)**는 다음과 같습니다.

| 관찰 | 해석 |
|------|------|
| 크기가 4×4로 고정 | 3×3보다 제약·탐색이 복잡하고, 5×5 이상보다 다루기 쉬운 **중간 난이도** |
| 1~16 연속 정수 | 합이 고정됨(마방 상수 = 34) → **검증이 수식으로 가능** |
| “프로그램” 언급 | 수학 퍼즐을 **알고리즘·자료구조·조건 검사**로 옮기는 연습 |
| 설계·구현을 미룸 | 구현 전에 **문제 정의·요구사항**을 분리하려는 의도 |

**4×4를 선택하는 이유(관찰 요약)**  
- 규칙이 명확해 **성공/실패를 기계적으로 판별**할 수 있음  
- 경우의 수·구성 방법이 3×3보다 풍부해 **탐색·휴리스틱·패턴**을 배우기 좋음  
- 여전히 손·코드로 **전체를 그려 검증**하기에 부담이 적음  

“마방진을 만든다”가 아니라, **“고정된 합 조건 아래에서 유효한 16칸 배치를 어떻게 얻고 확인할 것인가”**를 다루기 위해 4×4가 선택된 것으로 보입니다.

---

## 3. 이 문제는 어떤 학습 또는 시스템 설계 맥락에서 등장하는가?

### 학습 맥락

- **이산수학·조합**: 제약 만족, 순열/배치, 대칭·패턴  
- **알고리즘 입문**: 무작위 시도 vs 체계적 구성(Siamese 등), 백트래킹, 브루트포스  
- **프로그래밍 기초**: 2차원 배열, 반복·합산, 불변식(invariant) 검증  
- **문제 해결 프로세스**: 관찰 → 정의 → 설계 → 구현 순서를 **의도적으로 분리**하는 연습(지금 STEP 1이 그에 해당)

### 시스템 설계 맥락(작은 시스템이라도)

- **도메인**: “격자 + 16개 라벨 + 선별 합 균형”  
- **핵심 연산**: 배치 생성, 배치 검증, (선택) 해 탐색·출력  
- **품질 기준**: 올바른 배치만 허용, 중복·누락 숫자 거부, 합 34 일치  
- **미결정 요소**(관찰상 아직 없음): CLI/GUI, 사용자 입력 vs 자동 생성, 하나 vs 전체, 성능·확장(5×5) 여부  

빈 저장소라 **과제 명세서, 수업, 개인 프로젝트** 중 어디에 속하는지는 외부 문서 없이는 단정할 수 없습니다. 다만 **“작은 제약 만족 시스템을 처음부터 정의하는 연습”** 맥락에서는 전형적으로 등장하는 문제 유형입니다.

## 관찰 관점 한 줄 요약

> **16개의 서로 다른 정수를 4×4 격자에 놓았을 때, 여러 방향의 합이 하나의 값으로 맞는지를 다루는 상황**이며,  
> 그것을 **검증·생성·탐색** 중 무엇으로 할지는 아직 열린 상태이고,  
> **4×4는 규칙이 분명하면서도 알고리즘·구조를 배우기에 적당한 크기**로 보인다.

## Q: 왜 마방진을 완성해야 하는가?

“완성”은 여기서 **16칸을 채워 행·열·대각선 합이 모두 같아지는 상태에 도달하는 것**으로 둡니다. 검증만 하는 시스템에서는 **완성은 프로그램의 의무가 아니라 사용자(또는 과제·규칙) 쪽의 목표**입니다.

### 1. 과제·규칙이 “완성”을 성공 조건으로 정함

- 수업·책·시험에서 **“4×4 마방진을 완성하라”**가 제출·채점 기준일 수 있음.
- 프로그램은 **맞았는지 틀렸는지**만 알려 주고, **통과 여부는 “완성(=모든 선의 합 일치)”**에 달림.
- **왜 완성해야 하나:** 외부 평가·학습 목표가 “유효한 배치 하나를 스스로 만드는 것”이기 때문.

### 2. 사용자가 스스로 “맞는 배치”에 도달하고 싶음

- 퍼즐·연습으로 **16칸을 채우다가 “이제 다 맞나?”**를 확인하려 함.
- 검증기는 **시행착오의 종착점**을 알려 줌: 더 채울지, 고칠지, 포기할지 결정.
- **왜 완성해야 하나:** “내가 만든 배치가 진짜 마방진인가”라는 **불확실성을 없애기** 위함.

### 3. 완성하지 않으면 검증 결과가 의미 없거나 모호함

- 빈 칸·중복·범위 밖 숫자가 있으면 “합이 34인가”만으로는 **성공/실패를 단정하기 어려움**.
- **완성(또는 완성에 가까운 상태)**이어야 “행·열·대각선 모두 동일 합”이라는 **최종 판정**이 성립함.
- **왜 완성해야 하나:** 검증 규칙이 **“가득 찬, 1~16 각 1회”** 전제의 **최종 심사**이기 때문.

### 4. (암묵적) 학습 목표: 제약을 몸으로 이해함

- 자동 생성 없이 직접 채우면 **합 34, 대칭·쌍·행 분배** 같은 구조를 경험함.
- **왜 완성해야 하나:** “만드는 과정”이 학습이고, 완성은 그 과정의 **증명**이기 때문.

---

**한 줄로:**  
검증만 하는 시스템에서 마방진을 완성해야 하는 이유는, **외부 과제·자기 확인·최종 판정 가능 상태·학습 증명**을 위해 **“유효한 전체 배치”라는 목표 상태**에 도달해야 하기 때문입니다. 프로그램은 그 목표를 대신 달성하지 않습니다.

---

## 그 답에서 드러나는 불편함·구조적 문제

### A. 목표(완성)와 도구(검증)의 역할 불균형

| 구조 | 내용 |
|------|------|
| 사용자 부담 | 탐색·수정·힌트는 전부 사람에게 남음 |
| 프로그램 부담 | 끝난 뒤 **예/아니오(또는 어디가 틀렸는지)**만 가능 |
| 불편함 | “왜 안 되는지 / 다음에 뭘 할지”는 검증만으로는 **자주 부족** → 완성까지 **시간·좌절**이 사용자 쪽에 쏠림 |

**구조적 문제:** 시스템이 **문제 해결 파트너가 아니라 채점기**에 가깝다. “왜 완성해야 하나”에 대한 답(과제·확인·판정)은 명확하지만, **완성을 돕는 기능은 설계 밖**이라 목표와 지원이 어긋난다.

### B. 완성 전·완성 중 상태에 대한 모호함

- 빈 칸이 있으면: “아직 진행 중”인지 “이미 실패”인지 **검증 규칙만으로는 구분이 애매**할 수 있음.
- 일부만 맞는 합: “거의 다 왔다” vs “근본적으로 잘못됨”을 **단일 합검사로 구분하기 어려움**.
- **불편함:** 사용자는 **중간 피드백**(몇 줄 맞음, 어떤 제약 위반)을 원하는데, “완성해야만 의미 있는 최종 검증” 구조와 충돌.

**구조적 문제:** 성공 조건은 **이진(완성 vs 미완성)**인데, 실제 작업은 **연속(채워 가는 과정)**이다. **상태 모델이 과정과 맞지 않음**.

### C. 완성의 비용 대비 검증 정보의 빈약함

- 4×4라도 직접 채우면 **시행착오 횟수**가 많음.
- 검증이 “전체 틀림”만 알려 주면 **어느 칸·어느 선을 고칠지** 사용자가 다시 추론해야 함.
- **불편함:** 완성해야 하는 이유(확인·채점)는 강한데, **실패 시 회복 비용**은 검증 설계만으로는 줄지 않음.

**구조적 문제:** **피드백 granularity(입력 전체 vs 위반 위치 vs 힌트)**가 요구(완성)에 비해 너무 거칠 수 있다.

### D. “완성” 정의와 검증 전제의 정합성

- 완성 = 1~16 각 1회 + 모든 선 합 동일.
- 사용자가 실수로 **중복·누락·범위 밖**을 넣으면 “합” 검사 전에 **실패 유형이 여러 개**.
- **불편함:** 사용자 입장에서는 “마방진이 안 된다” 하나로 느끼지만, 시스템은 **형식 오류 vs 합 불일치**를 나눠야 함 → 메시지·우선순위 설계 부담.

**구조적 문제:** 단일 질문(“마방진인가?”)에 **다층 제약(존재·유일·합)**이 묶여 있어, 검증만 해도 **내부적으로는 다단계 판정**이 필요하다.

### E. 학습 목표와 검증-only의 긴장

- “왜 완성해야 하나”에 **학습**이 포함되면, 검증만으로는 **탐색 전략·패턴**을 가르치지 못함.
- 맞추면 학습 종료, 틀리면 **어디서 개념이 틀렸는지** 연결 안 됨.
- **구조적 문제:** **목적(이해)과 수단(최종 판정)**이 분리됨 → 같은 UI라도 **연습용**과 **채점용** 요구가 다를 수 있는데, 가정 하나로는 둘 다 설명이 부족함.

### F. 책임 경계

- 완성 실패: 사용자 탓인가, 문제 난이도인가, 검증 메시지 부족인가 **시스템 경계에서 불명확**.
- **구조적 문제:** **성공은 사용자 성취, 실패는 사용자 입력**으로 귀결되기 쉬워, 제품/과제 설계 시 **지원 부재가 요구사항 누락인지 의도인지** 문서화되지 않으면 나중에 “생성 기능도 넣어 달라”로 요구가 밀림.

## 1. 반복 가능성

| 손 계산 | 프로그램 |
|--------|----------|
| 시도마다 집중력·시간이 달라짐 | 같은 입력에 대해 **동일한 절차·동일한 결과** |
| “이번엔 대각선을 빼먹었다” 같은 **누락**이 반복될 수 있음 | 검사 대상(4행, 4열, 2대각선, 16칸 값)을 **매번 빠짐없이** 돌림 |
| 여러 번 채워 보기(시행착오)할수록 **피로**가 누적 | N번째 시도도 1번째와 **같은 기준**으로 판정 |

**왜 프로그램인가:**  
마방진 연습은 **“채우기 → 검증 → 수정 → 다시 채우기”**가 반복된다. 손 계산은 반복할수록 실수 확률이 올라가고, 기준이 미묘하게 흔들릴 수 있다. 프로그램은 **판정 절차를 고정**해, 연습 횟수가 늘어도 **비교 가능한 피드백**을 준다.

**드러나는 점:** 반복 가능성의 목적은 “빠르게 계산”이 아니라 **“매번 같은 심사관”**을 두는 것이다.

---

## 2. 검증 자동화

4×4 마방진의 **완성 판정**은 규칙이 분명하다.

- 16칸이 모두 채워졌는가  
- 1~16이 각각 정확히 한 번인가  
- 10개 선(행 4 + 열 4 + 대각선 2)의 합이 모두 같은가(4×4에서 마방 상수 34)

손으로는 **10번의 합산 + 중복·누락 확인**이 필요하고, 사용자는 종종 “행만 맞으면 됐지”처럼 **일부만** 확인한다.

**왜 프로그램인가:**  
위 조건은 **if / 반복 / 합산**으로 옮기기 좋은 **명시적 규칙**이다. 사람이 매번 하던 검증을 **한 번에, 동시에, 전 항목** 실행하면:

- “거의 맞은 것 같다” → **전체 규칙 기준**으로 확정  
- 과제·자기 확인에서 요구하는 **최종 판정**을 즉시 수행  

**드러나는 점:** 자동화의 가치는 “계산기 대체”가 아니라 **다중 제약을 한꺼번에 적용**하는 것이다. STEP 2에서 말한 “완성해야만 의미 있는 최종 검증”을 **일관되게 실행**하는 도구가 된다.

---

## 3. 오류 방지

여기서 오류는 두 종류다.

**A. 사용자가 격자를 잘못 채운 오류**  
→ 프로그램이 **발견**하는 것이지, 프로그램이 **막지는** 못한다(직접 입력 가정).

**B. 검증 과정 자체의 오류**  
→ 프로그램이 **줄이는** 대상이다.

| 손 검증 시 흔한 실수 | 프로그램이 줄이는 방식 |
|---------------------|------------------------|
| 한 줄 합을 잘못 더함 | 합산 로직을 한곳에 두고 재사용 |
| 대각선·일부 열 생략 | 검사 목록을 코드로 고정 |
| 중복 숫자를 놓침 | 1~16 출현 횟수를 기계적으로 집계 |
| “34가 맞네”와 “전 줄 맞네” 혼동 | 모든 선을 같은 루프·같은 기준으로 처리 |

**왜 프로그램인가:**  
사용자의 **배치 오류**는 여전히 있을 수 있지만, **“맞다고 착각하는 검증 오류”**는 줄인다. 특히 피곤할 때·여러 번 시도할 때 손 검증 실수가 커지는데, 그때 **판정의 신뢰도**를 프로그램이 맡는다.

**드러나는 점:** 오류 방지는 “입력 검증(숫자만 받기)” 수준을 넘어, **판정 신뢰성**이 핵심이다. STEP 2의 “실패 시 어디가 틀렸는지”는 설계 선택이지만, **틀렸다/맞았다 자체를 잘못 알려 주는 것**은 프로그램이 막기 쉽다.

## 4. 규칙 기반 사고 훈련

“단순 계산”은 **결과(합이 34다)**에 머무르기 쉽다.  
프로그램으로 구현하면 **규칙을 문장·절차로 쪼개야** 한다.

예를 들면:

- **전제:** “판정하려면 16칸이 모두 유효한 정수여야 한다”  
- **불변식:** “유효한 4×4 마방진이면 모든 관련 선의 합이 같다”  
- **검사 순서:** 형식(빈 칸, 범위) → 유일성(1~16) → 선별 합  
- **출력:** 성공 / 실패 + (선택) 어떤 규칙 위반인지  

이는 **수학 퍼즐을 컴퓨터가 실행 가능한 규칙 집합**으로 번역하는 연습이다.

**왜 프로그램인가:**  
구현 과정에서 학습자는:

- 말로만 알던 “마방진”을 **검증 가능한 조건**으로 쓰고  
- 예외(빈 칸, 중복)와 본 조건(합 일치)을 **분리**하며  
- “사람이 대충 본다”와 “기계가 전부 본다”의 차이를 경험한다  

사용자가 칸을 채우는 역할은 그대로여도, **검증 규칙을 코드로 옮기는 쪽**에서 규칙 기반 사고가 강화된다.

**드러나는 점:** 훈련 목표는 “마방진 만들기 알고리즘”이 아니라 **“문제를 규칙·상태·판정으로 모델링하기”**에 가깝다. 4×4는 규칙이 짧아 **첫 모델링 연습**으로 적합하다.

---

## 네 관점을 한데 모은 답

**왜 단순 계산이 아니라 프로그램인가?**

손 계산도 4×4 한 장은 가능하지만, **반복 연습·다중 제약 검증·판정 신뢰·규칙의 명시화**에서는 한계가 있다.  
프로그램은 **같은 기준으로 무한히 다시 판정**하고(반복 가능성), **10개 선과 16개 숫자 제약을 빠짐없이 검사**하며(검증 자동화), **“맞다고 잘못 확인하는” 실수를 줄이고**(오류 방지), **마방진 조건을 실행 가능한 규칙으로 다루는 연습**(규칙 기반 사고)을 가능하게 한다.

검증-only 가정에서는 **생성·힌트는 범위 밖**이어도, **“채운 뒤의 심사”**만으로도 위 네 가지 이유가 성립한다.

---

## 이 답에서 드러나는 구조적 메모 (STEP 3 관찰)

1. **프로그램의 핵심 가치는 “계산 속도”가 아니라 “판정의 재현성·완전성”**이다.  
2. **자동화 ≠ 사용자 오류 제거** — 배치는 여전히 사람, **판정 오류**를 줄이는 쪽이 주 효과다.  
3. **규칙 기반 사고**는 사용자 UI보다 **검증 로직을 설계·구현하는 사람**에게 먼저 적용된다(과제가 “검증기 만들기”일 때).  
4. STEP 2와 연결: 프로그램이 **완성을 대신하지 않아도**, “왜 완성해야 하나”에 대한 답(확인·채점)을 **신뢰할 수 있게 실행**하는 이유가 된다.

---

# STEP 4 — Why #3 (핵심 발견)  
**Q: 왜 이 문제를 TDD 방식으로 설계하려 하는가?**

**전제 정리:** 4×4 격자, 사용자가 칸을 채움, 프로그램은 **검증만** 수행. STEP 3까지의 결론은 “판정의 **재현성·완전성·규칙 명시화**”가 프로그램의 핵심 가치라는 것이다. TDD는 그 가치를 **설계 단계부터 강제하는 방법**으로 맞닿아 있다.

---

## 핵심 발견 (한 문장)

> **마방진 문제는 ‘창작’보다 ‘규칙에 따른 판정’이 중심이고, 판정은 예·아니오가 분명한 불변식들의 조합이므로, 테스트로 먼저 고정할 대상이 분명하다.**

즉 TDD를 쓰는 이유는 “유행해서”가 아니라, **검증기의 책임 경계가 수학적으로 잘려 있기 때문**이다.

---

## 1. 무엇이 통제되어야 하는가?

TDD에서 “통제”란 **의도한 규칙대로만 동작한다는 것을 증명하는 것**이다. 사용자가 칸을 어떻게 채우는지는 통제할 수 없고, **통제 대상은 검증 로직**이다.

| 통제 대상 | 통제하지 않는 것 |
|-----------|------------------|
| 주어진 4×4 배치에 대한 **성공/실패 판정** | 사용자의 탐색 전략·힌트·UI |
| **어떤 규칙을 어겼는지** (설계 시 선택) | “좋은” 배치 vs “나쁜” 배치의 미학 |
| 동일 입력에 대한 **결정적(deterministic) 결과** | 입력 순서·실험마다 달라지는 사람의 손계산 |
| 검사 **범위의 완전성** (10개 선, 1~16 유일성 등) | 4×4 이외 크기·다른 숫자 집합(범위 확장 전) |

**왜 TDD인가:**  
검증-only 시스템에서 버그는 “마방진을 못 만든다”가 아니라 **“틀린 것을 맞다고 하거나, 맞은 것을 틀리다고 한다”**다. TDD는 **판정 오류**를 통제 대상으로 올리고, 리팩터링·기능 추가(부분 검증, 메시지 분기) 때 **그 통제가 깨지지 않게** 한다.

STEP 2에서 본 **목표(완성) vs 도구(사후 판정) 불균형**은 TDD로 **“도구가 보장해야 할 최소 계약”**을 먼저 쓰면 완화된다. “사용자가 완성해야 한다”는 요구와 별도로, **“완성 여부를 잘못 알려 주지 않는다”**는 요구를 테스트가 대신한다.

---

## 2. 어떤 불변 조건이 존재하는가?

불변 조건(invariant)은 **상태가 어떻게 변해도(또는 어떤 입력에서도) 깨지면 안 되는 성질**이다. 4×4 마방진 검증에는 **수학적 불변식**과 **시스템 불변식**이 겹친다.

### (A) 도메인 불변식 — “유효한 마방진”이면 항상 참

- **크기:** 4×4, 16칸.
- **값 집합:** 1~16이 각각 정확히 1회(순열).
- **마방 상수:** 이 설정에서는 모든 관련 선의 합 = **34**.
- **선 집합:** 행 4 + 열 4 + 대각선 2 → **10개 선의 합이 서로 같음** (실제로는 “모두 34”와 동치).

이들은 **입력이 ‘완성된 유효 마방진’일 때** 동시에 만족해야 한다. 테스트는 **각 조건을 깨는 최소 반례**를 만들기 좋다(한 줄만 틀림, 중복 하나, 17 사용, 대각선만 틀림 등).

### (B) 검증기 불변식 — “프로그램이 항상 지켜야 할 것”

- **결정성:** 같은 `grid` → 같은 `result` (및 같은 부가 정보).
- **완전성:** 성공 판정은 (A) 전부 만족할 때만; 하나라도 위반 시 실패(또는 정의한 “부분 성공” 상태가 없다면 실패).
- **순서 독립:** 행을 먼저 검사하든 대각선을 먼저 검사하든 **최종 판정은 동일** (구현 세부가 결과를 바꾸지 않음).
- **단조적 엄격성(설계 선택 시):** 빈 칸·중복·범위 위반이 있으면 “합만 맞음”으로 성공 처리하지 않음.

**왜 TDD인가:**  
불변 조건은 **테스트 이름과 케이스로 그대로 옮길 수 있다.**  
예: “1~16 각 1회”, “모든 선 합 34”, “한 칸만 바꾼 변형은 실패”.  
RED → GREEN → REFACTOR 사이클이 **불변식을 문서화·회귀 방지**하는 장치가 된다. STEP 3의 “규칙 기반 사고 훈련”이 **테스트 목록 = 규칙 목록**으로 구체화된다.

## 3. 왜 입력/출력이 명확해야 하는가?

TDD는 **호출 가능한 단위**에 “주어진 입력 → 기대 출력”을 먼저 쓴다. 마방진 검증은 **I/O가 명확할수록 테스트가 쉽고, 모호할수록 TDD가 무너진다.**

### 입력이 명확해야 하는 이유

- **형식:** `4×4` 정수 배열인지, 평탄화 `length 16`인지, 빈 칸은 `0`/`null`인지.
- **완성도:** “16칸 모두 채움”만 검증할지, 빈 칸이면 **별도 실패 코드**인지.
- **범위:** 1~16만 허용인지, 그 외는 즉시 실패인지.

입력 정의가 흐리면 “거의 맞은 격자”를 **성공으로 볼지 실패로 볼지** 테스트가 작성되기 전에 팀마다 다르게 구현된다. STEP 2의 **진행 중 vs 완성** 모호함을 **타입·계약·첫 테스트**로 잘라야 한다.

### 출력이 명확해야 하는 이유

- **최소:** `boolean` (마방진 여부).
- **확장(요구 시):** `enum` 실패 사유, 틀린 선 인덱스, 기대 합 vs 실제 합.
- **부작용 없음:** 검증은 **순수 함수**에 가깝게 두면 테스트가 **설정·DB·UI 없이** 돌아간다.

출력이 “맞아요/틀려요” 한 줄뿐이면 테스트는 단순하지만, STEP 2의 **실패 복구** 요구와 충돌할 수 있다. TDD는 그때 **출력 스펙을 먼저 테스트로 고정**해, “판정만”에서 “진단까지”로 범위를 키울지 **의도적으로** 결정하게 한다.

### TDD와 I/O 명확성의 관계 (요약)

| I/O가 명확할 때 | I/O가 모호할 때 |
|----------------|----------------|
| 표준·알려진 해와 변형만으로 **회귀 스위트** 구성 | “사용자 느낌”에 맞춘 애매한 통과 |
| 리팩터 후 `pytest`/`jest` 한 번에 **신뢰** | 리팩터가 **판정 의미**를 바꿈 |
| STEP 3 **반복 가능성**이 코드로 보장 | 반복 실행해도 **스펙 자체가 흔들림** |

**왜 TDD인가:**  
명확한 I/O는 TDD의 **전제 조건**이자 **산출물**이다. “검증 함수 `verify(grid) -> Result`”처럼 경계를 긋는 행위가 곧 문제 정의의 마무리에 가깝다.

## 세 질문을 엮은 최종 답

**왜 TDD로 설계하려 하는가?**

1. **통제:** 사용자 창작이 아니라 **판정의 정확성·결정성·검사 완전성**을 통제해야 하고, 그건 자동 테스트 없이는 반복 연습·리팩터에서 쉽게 무너진다.  
2. **불변 조건:** 1~16 유일성, 10개 선 합 34 등 **수학적 불변식**과 **동일 입력 → 동일 결과** 같은 **시스템 불변식**이 있어, 테스트가 곧 스펙이 된다.  
3. **I/O:** `grid`와 `Result`를 먼저 고정해야 STEP 2의 **이진 완성 vs 연속 채우기** 갈등이 구현 전에 **계약**으로 정리되고, TDD 사이클이 의미를 갖는다.

**핵심 발견:**  
이 문제는 TDD에 **잘 맞는 문제 유형**(순수 판정, 풍부한 반례, 명시적 불변식)이다. 반대로 TDD가 **어렵게 만드는 것**은 “마방진을 예쁘게 만드는 법”이 아니라, **입력(빈 칸·부분 채움)과 출력(실패 이유)을 아직 정하지 않은 채 코딩하는 것**이다. 따라서 TDD를 선택한다는 것은 **구현 기법 선택**이면서 동시에 **“검증 계약을 먼저 쓰겠다”는 문제 정의 선언**이다.

# STEP 5 — 진짜 문제 정의

**맥락:** 4×4 격자, 1~16을 한 번씩 사용, 사용자가 칸을 채움, 시스템은 **판정(검증)**만 담당. TDD는 **판정 계약과 불변식**을 먼저 고정하는 방식으로 접근.

---

## 1. 표면 문제 정의 (잘못된 정의)

> **“4×4 마방진을 만드는 프로그램을 만든다.”**

| 왜 잘못된가 | 설명 |
|------------|------|
| 목표가 생성 쪽으로 치우침 | 실제 가정은 **사용자가 채우고, 시스템은 맞는지 판단**하는 것 |
| “마방진”이 모호함 | 완성·부분 채움·거의 맞음·한 줄만 맞음을 구분하지 않음 |
| 성공이 누구의 책임인지 불명확 | 프로그램이 “해를 낸다” vs 사용자가 “맞춘다”가 섞임 |
| 품질 기준이 없음 | 빠르게 하나 보여 주기 vs **틀리지 않고 판정하기**가 다름 |
| 학습 목표가 숨음 | 퍼즐 풀이 기술과 **규칙·판정·계약** 훈련이 구분되지 않음 |

**표면 정의가 만드는 착각:**  
기능 목록(입력, 출력, 화면)부터 시작하게 되고, **“언제 무엇이 성공인가”**가 나중에 붙는다.

---

## 2. 개선된 문제 정의 (정확한 정의)

> **“사용자가 제시한 4×4 정수 배치가, 1부터 16까지 각각 정확히 한 번씩 쓰였고, 지정된 모든 행·열·대각선에서 합이 동일한지를, 명시된 규칙에 따라 일관되게 판정하는 검증 책임을 갖는다.”**

### 문제의 본질

- **하지 않는 것:** 마방진을 대신 완성하거나, 최적 배치를 찾거나, 풀이 전략을 가르치는 것(범위 밖으로 둘 때).
- **하는 것:** 주어진 배치가 **사전에 정한 완성 기준**을 만족하는지 **신뢰할 수 있게** 판정하는 것.
- **성공:** 동일한 배치에 대해 **항상 같은 판정**이 나오고, 유효한 완성 배치는 통과·위반 배치는 통과하지 않음(오판 최소화).
- **실패(시스템 관점):** 맞는 배치를 틀렸다고 하거나, 틀린 배치를 맞다고 하는 것; 또는 검사 항목을 빠뜨려 판정이 흔들리는 것.

### 범위 경계 (의도적으로 열어 둔 결정)

| 항목 | 정의에 포함 | 별도 결정 필요 |
|------|-------------|----------------|
| 16칸 모두 채움 여부 | 완성 판정의 전제로 명시 | 빈 칸·미완성 시 별도 상태로 볼지 |
| 실패 이유·위치 안내 | 정의의 **선택 확장** | “맞다/틀리다”만 할지, 진단까지 할지 |
| 사용자 경험(화면·입력 방식) | 본 문제 정의 **밖** | 표현 계층은 다른 문제 |

### 한 문장 요약

**“완성된 4×4 배치가 마방진 조건을 만족하는지, 누가 채웠든 같은 기준으로 정확히 판정한다.”**

---

## 3. 이 문제의 핵심 Invariant

불변 조건은 **깨지면 “마방진 검증”이 아니게 되는 성질**이다. 도메인(수학)과 시스템(판정)을 구분한다.

### A. 도메인 Invariant — “유효한 완성 마방진”이면 항상 참

| ID | 불변 조건 |
|----|-----------|
| D1 | 격자는 4×4이며 16칸 모두 값이 있다 |
| D2 | 사용된 값은 1~16이며, 각 값은 정확히 한 번만 나타난다 |
| D3 | 행 4개, 열 4개, 대각선 2개 — 총 10개 선 각각의 합이 같다 |
| D4 | 이 설정에서 그 공통 합은 34이다 (D2·D3와 함께 일관됨) |

**관계:** D2가 깨지면 D3·D4만 맞아도 “유효 마방진”으로 보지 않는다. 판정은 **조건 묶음 전체**를 대상으로 한다.

### B. 시스템 Invariant — “검증 책임”이 지켜야 할 것

| ID | 불변 조건 |
|----|-----------|
| S1 | **결정성:** 같은 배치 입력 → 같은 판정 결과(및 정의된 부가 정보) |
| S2 | **완전성:** 성공은 D1~D4를 **모두** 만족할 때만 허용 |
| S3 | **건전성:** D1~D4 중 하나라도 위반 시 성공으로 판정하지 않음 |
| S4 | **검사 독립성:** 어떤 선·어떤 제약을 먼저 확인하든 최종 판정은 동일 |
| S5 | **역할 분리:** 배치 내용을 바꾸지 않고 판정만 수행(검증 행위가 입력을 변형하지 않음) |

### C. 테스트·계약 관점 Invariant (TDD와 연결)

| ID | 불변 조건 |
|----|-----------|
| T1 | 알려진 유효 완성 배치는 항상 성공 |
| T2 | 유효 배치에서 **단 하나의 조건만** 깨는 변형은 항상 실패 |
| T3 | 리팩터·표현 변경 후에도 T1·T2가 유지된다 |

**핵심 Invariant 한 줄:**  
**“1~16의 유일한 사용 + 10개 선의 동일 합”이 모두 참일 때만 성공이며, 그 판정은 입력마다 변하지 않고 빠짐없이 적용된다.**

## 4. 우리가 실제로 훈련하려는 사고 능력

구현·알고리즘이 아니라, **문제를 다루는 방식**을 훈련한다.

### 4.1 규칙 명시화

- 말로만 알던 “마방진”을 **검사 가능한 조건 묶음**(값 범위, 유일성, 선별 합)으로 쪼갠다.
- “거의 맞음”과 “조건 만족”을 **언어적으로 구분**한다.

### 4.2 책임·경계 구분

- **누가 채우는가**(사용자) vs **누가 판정하는가**(시스템)를 분리한다.
- 표면 요구(“만들어 줘”)와 실제 책임(“맞는지 판정”)의 **차이를 문제 정의 단계에서 바로잡는다**.

### 4.3 불변식 사고

- “항상 참이어야 하는 것”(D1~D4, S1~S5)을 먼저 적고, 기능은 그 **보호막** 아래에 둔다.
- 하나의 조건만 깨도 전체 실패인 **다중 제약**을 다룬다.

### 4.4 계약·입출력 사고

- **무엇이 들어오면**(완성된 4×4 배치 vs 미완성) **무엇이 나가야 하는지**(성공/실패, 선택적 진단)를 구현 전에 고정한다.
- 모호한 I/O는 버그가 아니라 **정의 오류**임을 인식한다.

### 4.5 판정 신뢰·재현성 사고 (STEP 3·4와 연결)

- 반복 연습·여러 번 시도에서 **판정 기준이 흔들리지 않게** 하는 것이 가치임을 안다.
- 사람의 손검산 실수와 **시스템이 막아야 할 오류(오판·누락 검사)**를 구분한다.

### 4.6 검증 주도 문제 정의 (TDD 정신, 코드 없이)

- “먼저 돌아가게”가 아니라 **“먼저 깨지면 안 되는 것을 적는다”**.
- 유효 사례·최소 반례·경계(빈 칸, 중복, 한 줄만 틀림)를 **요구의 일부**로 본다.

### 훈련 목표 요약

| 훈련하지 않는 것 (본 문제의 중심 아님) | 훈련하는 것 |
|--------------------------------------|-------------|
| 마방진 구성 기법·패턴 암기 | 조건 분해·불변식·판정 계약 |
| UI·프레임워크 사용 | 책임 경계·다중 제약 성공 정의 |
| “일단 돌아가는” 구현 | 재현 가능한 심사 기준과 오판 방지 |
