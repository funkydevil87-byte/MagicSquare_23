## STEP 1 — Observation (관찰)

### 1. 현재 우리가 해결하려는 상황은 무엇인가?

**한 사람이 4×4 격자에 1부터 16까지의 정수를 한 번씩 배치했을 때, 행·열·대각선 합이 모두 같은 “균형 조건”을 만족하는 배치를 찾거나 검증·생성하려는 상황**이다.

관찰 관점:

- **입력/출력:** 16칸 격자와 16개의 서로 다른 숫자(1~16)가 주어지거나, 시스템이 그런 배치를 제시함
- **제약:** 각 숫자는 정확히 한 칸에만 존재; 여러 “선(line)”(4행, 4열, 2대각선)의 합이 동일해야 함
- **불확실성:** “모든 배치”를 나열할지, “하나만” 만들지, “유효한지 검사”만 할지는 아직 명시되지 않음
- **맥락:** 학습·연습용 과제로 문제를 먼저 정의하려는 단계

즉, **“16개 숫자의 배치가 여러 선의 합 균형을 만족하는지, 어떻게 그런 배치에 도달하는지”**를 다루는 상황이다.

### 2. 왜 4×4 마방진 문제를 다루는가?

| 관찰 | 해석 |
|------|------|
| 크기가 4×4로 고정 | 3×3보다 제약·탐색이 복잡하고, 5×5 이상보다 다루기 쉬운 **중간 난이도** |
| 1~16 연속 정수 | 합이 고정됨(마방 상수 = 34) → **검증이 수식으로 가능** |
| “프로그램” 언급 | 수학 퍼즐을 **알고리즘·자료구조·조건 검사**로 옮기는 연습 |
| 설계·구현을 미룸 | 구현 전에 **문제 정의·요구사항**을 분리하려는 의도 |

**4×4를 선택하는 이유:** 규칙이 명확해 성공/실패를 기계적으로 판별할 수 있고, 경우의 수·구성 방법이 3×3보다 풍부하며, 여전히 손·코드로 전체를 검증하기에 부담이 적다.

### 3. 이 문제는 어떤 학습 또는 시스템 설계 맥락에서 등장하는가?

**학습 맥락**

- 이산수학·조합: 제약 만족, 순열/배치
- 알고리즘 입문: 체계적 구성 vs 시행착오, 탐색
- 프로그래밍 기초: 2차원 배열, 합산, 불변식 검증
- 문제 해결 프로세스: 관찰 → 정의 → 설계 → 구현 순서 분리

**시스템 설계 맥락 (소규모)**

- 도메인: 격자 + 16개 라벨 + 선별 합 균형
- 핵심 연산: 배치 생성, 배치 검증, (선택) 해 탐색·출력
- 품질 기준: 올바른 배치만 허용, 중복·누락 거부, 합 34 일치

### STEP 1 한 줄 요약

> 16개의 서로 다른 정수를 4×4 격자에 놓았을 때, 여러 방향의 합이 하나의 값으로 맞는지를 다루는 상황이며, 검증·생성·탐색 중 무엇으로 할지는 아직 열린 상태이다.

## STEP 2 — Why #1

**질문:** 왜 마방진을 완성해야 하는가?  
**가정:** 사용자가 직접 칸을 채우고, 프로그램은 검증만 한다.

### 답: 왜 완성해야 하는가

1. **과제·규칙** — “유효한 배치 하나를 스스로 만드는 것”이 제출·채점 기준
2. **자기 확인** — “내가 만든 배치가 진짜 마방진인가”라는 불확실성 제거
3. **최종 판정** — 16칸·1~16 각 1회 전제에서만 “모든 선 합 동일” 판정이 성립
4. **학습 증명** — 만드는 과정이 학습이고, 완성은 그 과정의 증명

**한 줄:** 외부 과제·자기 확인·최종 판정·학습 증명을 위해 **유효한 전체 배치**에 도달해야 한다. 프로그램은 그 목표를 대신 달성하지 않는다.

### 드러난 불편함·구조적 문제

| 구분 | 내용 |
|------|------|
| A. 역할 불균형 | 목표(완성)는 사용자, 도구는 사후 판정 → “다음에 뭘 할지” 부족 |
| B. 상태 모호 | 성공은 이진(완성), 작업은 연속(채워 가기) → 중간 피드백과 충돌 |
| C. 피드백 거침 | 실패 시 회복 비용이 사용자에게 쏠림 |
| D. 다층 제약 | 형식 오류 vs 합 불일치를 나눠야 하나 사용자는 하나로 느낌 |
| E. 학습 vs 채점 | 검증만으로는 탐색 전략·패턴을 가르치지 못함 |
| F. 책임 경계 | 실패 원인이 사용자·난이도·메시지 부족 중 어디인지 불명확 |

**STEP 2 핵심:** 목표는 **완성(이진)**인데 작업은 **진행(연속)**이고, 도구는 **사후 판정**에 머문다.

## STEP 3 — Why #2

**질문:** 왜 단순 계산이 아니라 프로그램으로 구현하는가?

### 1. 반복 가능성

- 같은 입력 → 동일한 절차·동일한 결과
- N번째 시도도 1번째와 같은 기준으로 판정
- **목적:** “매번 같은 심사관”

### 2. 검증 자동화

- 16칸 채움, 1~16 유일성, 10개 선(행4+열4+대각2) 합 동일을 **한꺼번에** 적용
- **목적:** 다중 제약을 누락 없이 적용

### 3. 오류 방지

- 사용자 배치 오류는 **발견**; 검증 과정의 덧셈 누락·대각선 생략 등은 **감소**
- **목적:** “맞다고 착각하는 검증 오류” 방지

### 4. 규칙 기반 사고 훈련

- 마방진 조건을 **검사 가능한 조건 묶음**으로 번역
- 전제·불변식·검사 순서·출력을 분리하는 연습
- **목적:** 실행 가능한 규칙으로 모델링

### STEP 3 종합

프로그램의 핵심 가치는 **계산 속도**가 아니라 **판정의 재현성·완전성**이다. 검증-only에서도 네 가지 이유가 성립한다.

## STEP 4 — Why #3 (핵심 발견)

**질문:** 왜 이 문제를 TDD 방식으로 설계하려 하는가?

### 핵심 발견 (한 문장)

> 마방진 문제는 ‘창작’보다 ‘규칙에 따른 판정’이 중심이고, 판정은 예·아니오가 분명한 불변식들의 조합이므로, 테스트로 먼저 고정할 대상이 분명하다.

### 1. 무엇이 통제되어야 하는가?

**통제 대상:** 판정의 정확성·결정성·검사 완전성·오판 방지  
**통제하지 않음:** 사용자 탐색, UI, 생성·힌트(범위 밖일 때)

버그의 본질: “못 만든다”가 아니라 **“틀린 것을 맞다고 하거나, 맞은 것을 틀리다고 한다.”**

### 2. 어떤 불변 조건이 존재하는가?

**도메인 불변식 (유효 완성 마방진)**

- 4×4, 16칸 모두 값 존재
- 1~16 각 1회
- 10개 선의 합이 모두 같음 (= 34)

**시스템 불변식 (검증 책임)**

- 결정성, 완전성, 검사 순서 독립, (선택) 형식 위반 시 합만으로 성공하지 않음

**테스트·계약**

- 알려진 유효 배치 → 항상 성공
- 한 조건만 깨는 최소 반례 → 항상 실패
- 리팩터 후에도 위 유지

### 3. 왜 입력/출력이 명확해야 하는가?

- **입력:** 4×4 형식, 빈 칸 표현, 1~16 외 값 처리, 완성 vs 미완성
- **출력:** 성공/실패 최소; 확장 시 실패 유형·위치
- **I/O 명확성** = TDD 전제이자 산출물; 모호하면 스펙 자체가 흔들림

### STEP 4 종합

TDD 선택 = 구현 기법이면서 동시에 **“검증 계약을 먼저 쓰겠다”는 문제 정의 선언**.

## STEP 5 — 진짜 문제 정의

### 1. 표면 문제 정의 (잘못된 정의)

> **“4×4 마방진을 만드는 프로그램을 만든다.”**

- 생성으로 치우침, “마방진” 모호, 책임 불명확, 품질 기준 없음, 학습 목표 숨음

### 2. 개선된 문제 정의 (정확한 정의)

> **“사용자가 제시한 4×4 정수 배치가, 1부터 16까지 각각 정확히 한 번씩 쓰였고, 지정된 모든 행·열·대각선에서 합이 동일한지를, 명시된 규칙에 따라 일관되게 판정하는 검증 책임을 갖는다.”**

| 구분 | 내용 |
|------|------|
| 하지 않음 | 대신 완성, 최적 배치 탐색, 풀이 전략 교육(범위 밖일 때) |
| 함 | 완성 기준 만족 여부를 신뢰할 수 있게 판정 |
| 시스템 실패 | 오판, 검사 누락, 판정 흔들림 |

**한 문장:** 완성된 4×4 배치가 마방진 조건을 만족하는지, 누가 채웠든 같은 기준으로 정확히 판정한다.

### 3. 핵심 Invariant

**도메인 (D1~D4)**

| ID | 조건 |
|----|------|
| D1 | 4×4, 16칸 모두 값 |
| D2 | 1~16 각 1회 |
| D3 | 10개 선의 합이 같음 |
| D4 | 공통 합 = 34 |

**시스템 (S1~S5)**

| ID | 조건 |
|----|------|
| S1 | 결정성 |
| S2 | 성공은 D1~D4 전부 만족 시만 |
| S3 | 하나라도 위반 시 성공 아님 |
| S4 | 검사 순서와 무관하게 동일 판정 |
| S5 | 판정만 수행, 배치 내용 변경 없음 |

**테스트·계약 (T1~T3)**

| ID | 조건 |
|----|------|
| T1 | 알려진 유효 배치 → 성공 |
| T2 | 단일 조건 위반 변형 → 실패 |
| T3 | 변경 후 T1·T2 유지 |

### 4. 훈련하려는 사고 능력

| 능력 | 설명 |
|------|------|
| 규칙 명시화 | 조건 묶음으로 분해, “거의 맞음” vs “만족” 구분 |
| 책임·경계 구분 | 채우기 vs 판정, 표면 요구 vs 실제 책임 |
| 불변식 사고 | D·S 불변식을 먼저 적고 기능은 그 아래 |
| 계약·I/O 사고 | 구현 전 입출력·완성 정의 고정 |
| 판정 신뢰·재현성 | 오판·누락 검사가 시스템이 막을 오류 |
| 검증 주도 정의 | 먼저 깨지면 안 되는 것을 적기, 반례를 요구의 일부로 |

**훈련하지 않는 것 (본 문제 중심 아님):** 구성 기법 암기, UI 프레임워크, “일단 돌아가는” 구현
